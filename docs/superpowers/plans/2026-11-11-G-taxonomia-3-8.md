# Subsistema G: Tarea 3.8, clasificación por departamento y tipo Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recomendado) o superpowers:executing-plans para implementar este plan tarea por tarea. Los pasos usan checkbox (`- [ ]`) para seguimiento.

**Goal:** Cada producto nuevo entra con un tipo global (Playeras, Tenis…) válido para su departamento; el estilo (polo) y el "para" (dama/caballero/niño, solo Calzado) quedan como atributos; las ventas copian el tipo; existe la consulta base de stock por tipo y tienda; y los productos viejos se rellenan con un script idempotente.

**Architecture:** `ProductType` global + puente `DepartmentProductType`. `Product` gana `productTypeId`, `style` y `audience` (columnas dedicadas, validadas contra listas en código). `SaleLine` gana una copia sin FK de `productTypeId`. Durante la transición `Product.category` = `ProductType.name`, escrito solo por el servidor. Migración aditiva con `prisma migrate`; relleno en TypeScript (`prisma/scripts/backfill-product-types.ts`), nunca SQL a mano.

**Tech Stack:** Next.js 14.2 (App Router, server actions), React, TypeScript, Prisma 5.22 sobre PostgreSQL, Vitest (`npm test`) y pruebas de base (`npm run test:db`, `*.db.test.ts` con `describe.skipIf`).

**Orden de mezcla (cronograma §3):** Task 1 (migración 1) se mezcla **sola y primero**, el jueves 12, en un PR propio desde `feat/tipos-producto`; después H genera la migración 2 encima. Tasks 2–8 se mezclan después de la migración de H y **antes de D**: D construye sobre `NewProductInput`, `createProductAction`, `listProductTypesAction` y `ClassificationFields` de este plan, sin reescribirlos.

**Spec:** `docs/superpowers/specs/2026-11-10-taxonomia-productos-design.md` (addendum de v2; manda en caso de duda). Modelo: `docs/superpowers/specs/2026-11-05-modelo-datos-er.md` §2.9. Tarea origen: `docs/superpowers/plans/2026-11-09-implementaciones-posteriores.md` (Tarea 3.8). El spec ya está en `main` (PR #33, merge `d86ac21`).

## Global Constraints

- **Servidor decide el tipo:** `createProductAction` exige `productTypeId`; `NewProductInput` no tiene campo `category`. Cualquier `category` que mande el cliente se ignora. Sin texto libre temporal en la versión final.
- **Invariante:** con `productTypeId` no nulo, `Product.category === ProductType.name`. Solo el servidor escribe `category`.
- **Migración:** solo `prisma migrate`, aditiva. Sin `DROP`, `ALTER COLUMN`, `SET NOT NULL`, `CHECK`; ningún `ADD COLUMN` con `NOT NULL`. El SQL se genera contra Postgres **local** (`127.0.0.1`), nunca contra Neon. No se edita el SQL a mano. Ningún dato en la migración.
